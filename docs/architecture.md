# 아키텍처 및 설계 노트

이 문서는 BOTTLENECK의 구성 요소별 책임, 확장 방향, 기술 선택의 트레이드오프를 정리한다.

---

## 1. HTML / CSS / JavaScript의 역할 분담

웹 프론트엔드는 세 가지 기술이 각각 다른 책임을 맡는다.
하나가 다른 하나의 역할을 대신하면 유지보수가 어려워지므로, 이 프로젝트에서는 아래 기준으로 분리했다.

### HTML — 구조(Structure)

**화면에 어떤 정보가 어떤 순서로 존재하는지를 정의한다.**
스타일이나 동작을 포함하지 않으며, CSS를 모두 걷어내도 문서로서 읽히는 것이 목표다.

`index.html`에서는 다음을 담당한다.

- 3개 섹션(`#home`, `#diagnose`, `#glossary`)의 구획과 순서
- 입력 폼의 필드 구성과 각 입력의 의미(`<label>`과 `for` 속성 연결)
- 결과가 표시될 빈 컨테이너(`#result`)와 그 내부 요소들의 자리

결과 카드의 텍스트는 HTML에 없다. AI 응답이 오기 전까지 채울 내용이 없기 때문이며,
자리만 잡아두고 JavaScript가 값을 채운다.

### CSS — 표현(Presentation)

**같은 구조를 어떻게 보여줄지를 정의한다.**
`style.css`를 제거해도 정보는 그대로 남고 모양만 사라진다.

`css/style.css`에서는 다음을 담당한다.

- 색상 체계(시안·마젠타·앰버)와 정보 위계 표현
- 여백, 정렬, 카드 레이아웃
- 화면 폭에 따른 레이아웃 전환(`@media (max-width: 640px)`)
- 상태에 따른 시각적 변화(`.message--loading`, `:disabled`, `:focus`)

**로딩 상태의 색상 변경을 CSS 클래스로 처리한 이유**
JavaScript에서 `element.style.color = '#00f0ff'`처럼 직접 지정할 수도 있지만,
그러면 색상 정의가 CSS와 JS 두 곳에 흩어진다.
JS는 `.message--loading` 클래스를 붙이거나 떼는 일만 하고, 그 클래스가 어떻게 보이는지는 CSS가 결정한다.

### JavaScript — 동작(Behavior)

**사용자 입력에 반응해 상태를 바꾼다.**
`main.js`를 제거하면 화면은 그대로지만 진단 버튼이 아무 반응도 하지 않는다.

`js/main.js`에서는 다음을 담당한다.

- 입력값 수집 및 필수값 검증
- `fetch`로 백엔드 호출, 응답 대기 중 로딩 상태 전환
- 응답 JSON을 DOM 요소에 반영
- 실패 상황(빈 입력·API 오류·타임아웃·네트워크 단절) 분기 처리

### 세 기술의 협업 흐름

```
사용자가 "진단하기" 클릭
      ↓
[JS]  입력값 읽기 → 검증
      ↓
[JS]  버튼 비활성화 + 메시지 요소에 클래스 부여
      ↓
[CSS] .message--loading 규칙에 따라 시안색 안내 박스 렌더
      ↓
[JS]  fetch → 응답 수신 → HTML의 빈 컨테이너에 값 삽입
      ↓
[CSS] .result 규칙에 따라 카드 형태로 표시
```

JavaScript는 "무엇을 보여줄지"만 결정하고, "어떻게 보일지"는 CSS가 맡는다.

## 2. 파일별 책임

| 파일 | 계층 | 책임 |
| --- | --- | --- |
| `index.html` | 프론트 | 3개 섹션 구조, 입력 폼, 결과 표시 영역의 골격 |
| `css/style.css` | 프론트 | 색상 체계, 레이아웃, 반응형 분기, 상태별 시각 표현 |
| `js/main.js` | 프론트 | 입력 검증, fetch 호출, 응답 렌더링, 실패 처리 분기 |
| `api/hello.py` | 백엔드 | 배포 파이프라인 검증용 엔드포인트 |
| `api/diagnose.py` | 백엔드 | 프롬프트 구성, Gemini API 호출, 응답 파싱, 오류 상태 코드 매핑 |
| `requirements.txt` | 백엔드 | Serverless Function 실행에 필요한 외부 패키지 정의 |
| `.gitignore` | 인프라 | 환경 변수 파일 및 로컬 산출물의 커밋 차단 |

### 프론트와 백엔드를 나눈 기준

**API 키를 아는 쪽이 백엔드다.**
브라우저에서 직접 Gemini를 호출하면 키가 네트워크 탭과 소스 코드에 그대로 노출된다.
백엔드를 경유하면 브라우저는 `/api/diagnose`만 알고, 키는 Vercel 서버에만 존재한다.

이 경계 때문에 프롬프트 내용도 백엔드에 둔다.
프론트에서 프롬프트를 만들어 보내면 사용자가 프롬프트를 조작해
의도하지 않은 용도로 API를 사용할 수 있기 때문이다.

## 3. 확장 시나리오

현재 구조에서 기능을 추가할 때 어디를 수정해야 하는지 정리한다.

### 3-1. 입력 필드 추가 (예: 파워서플라이, 메인보드)

| 수정 대상 | 작업 |
| --- | --- |
| `index.html` | 입력 필드 마크업 추가 |
| `js/main.js` | 요청 본문에 필드 추가, 필수값이면 검증 로직 추가 |
| `api/diagnose.py` | `PROMPT_TEMPLATE`에 항목 추가, `body.get()` 추출 추가 |

**응답 스키마는 바뀌지 않는다.** 입력이 늘어도 출력 구조는 동일하므로 렌더링 코드는 수정 불필요하다.
선택 입력이라면 기존 방식대로 미입력 시 `"미입력"`으로 대체한다.

**영향 범위:** 프론트 2개 파일, 백엔드 1개 파일. 배포 후 기존 사용자 영향 없음.

### 3-2. 출력 항목 추가 (예: 예상 프레임, 전력 소비량)

| 수정 대상 | 작업 |
| --- | --- |
| `api/diagnose.py` | `PROMPT_TEMPLATE`의 JSON 스키마에 필드 추가 |
| `index.html` | 표시할 요소 추가 |
| `css/style.css` | 새 요소 스타일 |
| `js/main.js` | `renderResult()`에 삽입 로직 추가 |

**주의점:** AI가 새 필드를 항상 반환한다는 보장이 없다.
`renderResult()`에서 이미 `data.bottleneck || '판정 불가'`, `data.score ?? '-'`처럼
값이 없을 때의 기본값을 두고 있으므로, 새 필드도 같은 방식으로 처리해야 한다.
필드 하나가 없다고 화면 전체가 비는 상황을 막기 위해서다.

### 3-3. 멀티 모델 지원 (예: Gemini + OpenAI 선택)

가장 변경 범위가 큰 확장이다. 현재는 `api/diagnose.py`가 Gemini 호출을 직접 수행한다.

**필요한 구조 변경**

1. AI 호출부를 별도 함수로 분리해 `call_gemini(prompt)`, `call_openai(prompt)` 형태로 나눈다.
2. 각 함수가 **동일한 형태의 결과(파싱된 dict)를 반환**하도록 통일한다.
   제공사마다 응답 JSON 구조가 다르므로(Gemini는 `candidates[].content.parts[]`,
   OpenAI는 `choices[].message.content`) 이 차이를 함수 내부에서 흡수해야 한다.
3. 요청 본문에 `provider` 필드를 받아 분기한다.
4. 환경 변수를 제공사별로 등록한다(`GEMINI_API_KEY`, `OPENAI_API_KEY`).

**프론트엔드 영향**
응답 스키마가 동일하게 유지되면 `renderResult()`는 수정할 필요가 없다.
제공사 선택 UI와 요청 본문의 `provider` 필드만 추가하면 된다.

**이것이 JSON 스키마를 고정한 설계의 이점이다.**
AI 응답을 그대로 화면에 출력하는 방식이었다면 제공사가 바뀔 때마다 화면이 달라졌을 것이다.

### 3-4. 진단 이력 저장

현재는 상태를 저장하지 않는다(stateless). 이력 기능을 추가하려면 외부 저장소가 필요하다.

Serverless Function은 실행이 끝나면 메모리가 사라지고 파일 시스템도 유지되지 않으므로,
Vercel KV, Supabase 등 외부 데이터베이스를 연동해야 한다.
이 경우 개인정보 저장 여부와 보관 기간에 대한 정책을 함께 정의해야 한다.

## 4. 기술 선택의 트레이드오프

### 4-1. 바닐라 JavaScript vs 프레임워크

이번 과제는 프레임워크 사용이 금지되어 바닐라로 구현했다.
만약 React 등의 사용이 허용됐다면 어떤 차이가 있었을지 정리한다.

**바닐라의 장점 (현재 구조)**

- 빌드 과정이 없어 파일을 그대로 배포하면 동작한다. 배포 설정이 단순하다.
- 의존성이 없어 패키지 취약점 관리 부담이 없다.
- 브라우저가 HTML·CSS·JS를 어떻게 처리하는지 직접 확인할 수 있다.
- 초기 로딩 시 다운로드할 스크립트가 `main.js` 하나뿐이다.

**바닐라의 단점**

- DOM 조작을 직접 해야 한다. `renderResult()`에서 `createElement`와 `append`를 반복하는 부분이 그 예다.
- 상태와 화면의 동기화를 수동으로 관리한다. 결과를 새로 표시할 때
  이전 목록을 `innerHTML = ''`로 비우는 처리를 잊으면 항목이 누적된다.
- 화면이 늘어나면 요소 참조와 이벤트 리스너가 파일 하나에 쌓인다.

**React를 썼다면**

- `upgrades.map()` 한 줄로 목록이 렌더링되고, 상태가 바뀌면 화면이 자동 갱신된다.
- 컴포넌트 단위로 파일이 나뉘어 화면이 늘어나도 구조가 유지된다.
- 대신 빌드 도구, 노드 의존성, 번들 크기가 추가된다.

**예상 리팩토링 범위**

| 파일 | 변경 정도 |
| --- | --- |
| `js/main.js` | 전면 재작성 (컴포넌트 + 상태 훅) |
| `index.html` | 마운트 지점만 남기고 JSX로 이전 |
| `css/style.css` | 대부분 재사용 가능 (클래스명 유지 시) |
| `api/diagnose.py` | **변경 없음** |

백엔드가 영향을 받지 않는다는 점이 중요하다.
프론트와 백엔드가 JSON이라는 계약으로만 연결되어 있어, 한쪽 기술을 바꿔도 다른 쪽은 그대로다.

**결론**
이 규모(단일 페이지, 화면 상태 4가지)에서는 바닐라가 적절하다.
프레임워크의 이점은 화면과 상태가 많아질 때 나타나는데,
현재는 진단 요청 하나만 처리하므로 도입 비용이 이득을 넘어선다.

### 4-2. 공식 SDK vs REST 직접 호출

`google-generativeai` SDK 대신 `requests`로 REST를 직접 호출했다.

| 항목 | SDK | REST 직접 호출 (선택) |
| --- | --- | --- |
| 코드 길이 | 짧음 | 김 |
| 의존성 | 패키지 1개 + 하위 의존성 다수 | `requests` 하나 |
| 흐름 파악 | 내부에 감춰짐 | URL·헤더·본문이 코드에 노출 |
| 오류 진단 | SDK 예외로 추상화됨 | HTTP 상태 코드와 원문 응답 확인 가능 |

**REST를 선택한 이유**
디버깅 과정에서 404 응답의 원문을 직접 확인해야 했는데,
SDK를 썼다면 예외 메시지만 보고 원인을 좁히기 어려웠을 것이다.
학습 목적에서도 요청·응답의 실제 형태를 보는 편이 낫다고 판단했다.

**SDK가 유리한 경우**
스트리밍 응답, 함수 호출(function calling), 멀티모달 입력 등
프로토콜이 복잡한 기능을 쓸 때는 SDK가 처리해주는 부분이 많아진다.

### 4-3. Serverless vs 상시 실행 서버

| 항목 | Serverless (선택) | 상시 서버 |
| --- | --- | --- |
| 비용 | 요청당 과금, 미사용 시 0 | 시간당 과금 |
| 서버 관리 | 불필요 | OS·런타임 업데이트 필요 |
| 콜드 스타트 | 첫 요청 지연 발생 | 없음 |
| 실행 시간 제한 | 있음 | 없음 |
| 상태 유지 | 불가 | 가능 |

**Serverless를 선택한 이유**
과제 요구사항이기도 하지만, 트래픽이 간헐적인 서비스에 적합하다.
진단 요청은 사용자가 있을 때만 발생하므로 상시 서버는 대부분의 시간을 유휴 상태로 보낸다.

**제약**
실행 시간 제한이 있어 AI 응답이 오래 걸리면 함수가 강제 종료된다.
이 때문에 백엔드 타임아웃을 25초로 설정하고, 프론트에서는 15초에 먼저 끊도록 설계했다.
